## Что строим

**OPC UA SendBox** — публичная многопользовательская веб-песочница экосистемы Electroman, аналог
Modbus SendBox (`modbus-sendbox.electroman.by`) для стека OPC UA. Пользователь поднимает
виртуальный OPC UA сервер, генерирует теги и алармы и проверяет подключение своего клиента
(SCADA, HMI, UaExpert). Родственный десктопный проект — ModbusToolkit (интерфейс RU/EN).

## Стек (по ТЗ)

- Python 3.11+, FastAPI (REST для управления сессиями + WebSocket для live-логов и статуса).
- `asyncua` как ядро OPC UA.
- Состояние в памяти (dict) под блокировками, без БД.
- Тесты: `pytest` + `pytest-asyncio`. Стиль: PEP 8, type hints с проверкой mypy, docstrings.

## Планируемая архитектура

```
opcua-sendbox/
├── app/
│   ├── main.py             # FastAPI entrypoint
│   ├── session_manager.py  # потокобезопасный реестр сессий и портов
│   ├── opcua_worker.py     # запуск/остановка asyncua-сервера
│   └── models.py           # Pydantic-схемы
├── tests/{unit,integration}/
└── requirements.txt
```

Ключевые инварианты, которые затрагивают несколько модулей:

- **Одна сессия — один изолированный OPC UA сервер** на уникальном порту из диапазона 4840–5000.
  Endpoint вида `opc.tcp://host:port/electroman/`.
- **Реестр сессий и портов — общий ресурс.** Выделение и освобождение порта атомарны
  (`asyncio.Lock` в асинхронном коде, `threading.RLock` в синхронных участках). Двум сессиям
  никогда не должен достаться один порт.
- **Изоляция отказов:** падение или зависание сервера одного пользователя не должно ронять
  FastAPI-воркер и чужие сессии (отдельный процесс через `multiprocessing` или как минимум
  изолированная `asyncio.Task`).
- **Жизненный цикл:** `POST /api/sessions` возвращает `session_id`, `endpoint_url`, `web_ui_url`;
  `DELETE /api/sessions/{id}` останавливает сервер и освобождает порт; простаивающие сессии
  автоматически закрываются примерно через 30 минут.
- Генераторы тегов: синусоида, пила, случайное число, константа, с настраиваемым периодом.
  Алармы — события Alarm & Condition по расписанию или вручную.
- Аутентификация (JWT или API-ключи) нужна прежде всего для лимита активных сессий на пользователя.

## Обязательные тесты (по ТЗ)

- Unit: математика генераторов (форма синусоиды, границы случайных значений), валидация API.
- Интеграционные: реальный in-process `asyncua.Server` в фикстуре; клиент подключается к серверу,
  созданному через API, и видит, что значение тега обновляется.
- Две параллельные сессии: разные порты, данные не пересекаются.
- Гонки: 10 параллельных задач create/delete, проверка уникальности портов.
