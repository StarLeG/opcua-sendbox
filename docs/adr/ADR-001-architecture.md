# ADR-001 · Архитектура: процесс на сессию, IPC, общий сервер

- **Статус:** принято
- **Дата:** 2026-11-03
- **Задача:** TASK-001

## Контекст

ТЗ требует многопользовательскую песочницу: у каждого пользователя свой изолированный
OPC UA сервер, сбой одного пользователя не должен задевать других. ModbusToolkit
держит статический список демо-серверов, поэтому нужен ещё и постоянный адрес.

## Решения

1. **Отдельный процесс на каждый OPC UA сервер** (`multiprocessing`, контекст `spawn`
   на всех ОС одинаково). Зависание или утечка в одном сервере не блокирует event loop
   FastAPI и остальные серверы, процесс можно принудительно убить. Цена — около
   30–50 МБ памяти на сессию; общий лимит сессий (по умолчанию 50) держит её в рамках.

2. **Общий демо-сервер** на фиксированном порту 4840
   (`opc.tcp://opcua-sendbox.electroman.by:4840/electroman/`): постоянный,
   read-only, демо-набор тегов, история и события. Запускается в lifespan тем же
   `worker.py` с флагом `shared`, при падении перезапускается с backoff.

3. **Личные сессии** на портах 4841–5000. `PortAllocator` под `threading.RLock`
   выдаёт порт только после успешной проверки `bind`. `SessionManager` держит реестр
   под `asyncio.Lock`; запуск процесса и ожидание `ready` идут вне лока.

4. **IPC.** На сессию три `multiprocessing.Queue`:
   - команды (родитель → воркер): `add_tag`, `remove_tag`, `add_alarm`,
     `trigger_alarm`, `stop`;
   - **control** (воркер → родитель, без ограничения размера): `ready`, `write`,
     `alarm`, `error`, `client_count`, `stats`. Сообщения редкие и терять их нельзя;
   - **telemetry** (воркер → родитель, `maxsize=64`): `tag_values`, `log`.
   Сообщения — dict'ы, валидируемые Pydantic-моделями. Reader-поток на сессию
   передаёт их в event loop через `call_soon_threadsafe`.

5. **Backpressure telemetry — drop-newest.** Воркер не шлёт сообщение на каждое
   обновление тега, а отправляет полный снимок всех тегов не чаще `WS_STATE_HZ`.
   При переполнении очереди `put_nowait` ловит `queue.Full`, снимок выбрасывается,
   счётчик дропов растёт и уходит наверх в `stats` (метрика
   `sendbox_ipc_telemetry_dropped_total`). Почему не drop-oldest:
   (а) со стороны производителя у `multiprocessing.Queue` это атомарно не сделать;
   (б) каждый снимок полный, следующий заменяет потерянный, и live-график теряет одну
   точку, а не ломается. Дальше работает backpressure `WebStateBus` (ограниченная
   очередь на WS-клиента, отключение медленного клиента кодом 1013), как в Modbus SendBox.

## Инварианты

1. **Подключённый клиент = активная сессия.** `client_count` — число активных OPC UA
   сессий, а не TCP-соединений. Пока оно больше нуля, idle-таймер стоит; переход в 0
   запускает его заново. Потолок жизни сессии (4 ч) действует всегда.
2. **Телеметрия может теряться, control-события — нет.**
3. **Ни одна сессия не остаётся в `starting`/`stopping`.** Любая ошибка или отмена
   запуска откатывает запись и освобождает порт в `finally`.
4. **Event loop FastAPI не блокируется**: блокирующие вызовы `multiprocessing`
   выполняются через `asyncio.to_thread` или в reader-потоках.

## Последствия

- Старт сессии занимает около секунды (spawn и импорт asyncua) — приемлемо для песочницы.
- Состояние только в памяти: перезапуск сервиса закрывает все сессии и сбрасывает ключи.
